Summer School Optimism

The Project

  • Goal: Fit opinion spreading models to real-world network data.
  • Start: First year of grad school workshop.
  • Initial Code: Quick & dirty PyTorch implementation.

The Vibe

“It’ll be 6 months, tops, to a publication.” 🤡

The Descent

Feature Creep & Portability

Phase 1: Portability

  • Problem: 5 collaborators on Mac, Linux, and Windows.
  • “Solution”: JSON configs + nested Shell/Python wrappers.

Phase 2: The HPC (VACC)

  • Problem: Local prototyping vs. Cluster batch jobs.
  • “Solution”: J2 templating to auto-generate .sh scripts.

The Breaking Point

Architecture Overkill

Data & Concurrency

  • Filename char limits? Build an ORM.
  • SQLite locking? Move to MySQL.
  • MySQL behind firewall? Polymorphic IO.

Total Collapse

  • Agnostic formatters for every possible output.
  • Agnostic inputs for polymorphic data classes.
  • The End: 2026, no publication, the framework is now so convoluted my collaborators just start writing their own code from scratch in Jupter notebooks and force-pushing to main because they hate the code.

The Hard Truth

  • This was all my fault.

The Iron Rule of Scientific Software Development

  • If you take the time to build out code the right way you will never use it
  • If you write sloppy code it will bite you in the ass
  • Damned if you do. Damned if you don’t.

The Python Paradox

  • Python is a TERRIBLE language for scientific computing.
  • Nothing about the language is inherently good for science.
  • Most tools were developed by researchers as a “side-hustle.”
  • The Goal: How can we contort Python to be at least “okay”?

The Dirty Secret…

  • If you are a (non-bench) scientist in 2026: YOU ARE A SOFTWARE DEVELOPER.
  • Most of your time isn’t in the lab; it’s writing and running code.
  • Fact: Scientists are (mostly) bad software developers.

Logic of my Life

The eternal struggle: Time spent to automate vs. overhead accumulated.

The Good News

  • Fact: Claude Code is a better developer than you will ever be.
  • Fact: LLMs change the ROI on automation.
  • Fact: I basically never write code anymore.
  • Fact: Most LLM failures are failures of context, not reasoning.

The Vibe-Coder Thesis

“Being an effective vibe-coder is NOT about writing some super secret prompt; it is about ensuring the model has adequate context.”

Your Workflow

  • You have data/simulation parameters.
  • You have a model (statistical/ML/physics).
  • You want to run sweeps with different inputs.
  • You want to collect & visualize efficiently.
  • You want to turn plots into a publication.

Goal

Automate the plumbing so you can focus on the science.

Tools of the Trade

1. VSCode / Cursor

Modern IDE

  • You have no excuse not to use a modern IDE.
  • VIM/EMACS are strictly worse for total project velocity.

Anti-Pattern

  • Stop using Jupyter Notebooks for everything.
  • Notebooks are for exploration, not logic.

Doc: code.visualstudio.com | cursor.com

2. Project Structure

Modularity

  • Separate source code from sweeps.
  • Make your source code a python module.
  • Example: bert_adapter.py

Version Control

  • Git early, git often.
  • Collaborating? Use Pull Requests.
  • Example: README.md

Doc: git-scm.com

3. UV: The New Standard

  • Speed: Orders of magnitude faster than pip.
  • Reproducibility: uv.lock is non-negotiable.
  • Example: pyproject.toml

Reproducibility

If it doesn’t run on your collaborator’s machine, it’s not Science.

Doc: docs.astral.sh/uv

UV vs. Conda

The Problems

  • Local vs. Cluster: “I developed code locally, but the VACC env crashes.”
  • Collaboration: “It works for me, but my coworker has global numpy issues.”

The Solutions

  • Local Envs: Environments live in the project folder.
  • Reproducibility: Lockfile ensures byte-for-byte matching.
  • Example: pyproject.toml

Doc: docs.astral.sh/uv

4. Pydantic: Strong Typing

The Problems

  • Boilerplate: Constant manual parsing of nested lists/dicts.
  • Silent Bugs: Passing \(N \times M\) when \(M \times N\) was expected.

The Solutions

  • Validation: Catch errors at the boundary.
  • LLM Context: Gives models the precise “slots” needed.
  • Example: schema.py

Doc: docs.pydantic.dev

5. Snakemake: Orchestration

The Problems

  • Amnesia: “I changed code; what results are now invalid?”
  • Lost parameters: “How did I generate this figure 6 months ago?”

The Solutions

  • DAG Generation: knows exactly what needs to run.
  • Self-Documentation: The Snakefile is the record.
  • Example: Snakefile

Doc: snakemake.github.io

6. Testing

The Problems

  • Silent Regression: Results changed, and you don’t know why.
  • Vibe Blindness: Trusting LLM code without verification.

The Solutions

  • Unit Tests: Shape checks & Baselines.
  • Vibe Coding: Use tests to verify LLM logic.
  • Example: test_nlp_logic.py

Doc: docs.pytest.org | ruff.rs
